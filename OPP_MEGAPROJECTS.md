- **6 proposed scenario categories:** paraphrase recall, multi-hop/structured (graph-only), exact-fact (KV, vector should *not* win), temporal/superseded (updated fact beats stale), noise robustness (survives N unrelated memories + forgetting), true negative (no relevant memory exists — must return nothing). Open: how many scenarios per category is "enough" (10/25/50?), and who authors/labels them (Kruz specifies, or proposes-for-approval)?

Proposed starting target: **recall@5 ≥ 0.90, precision@1 ≥ 0.70** on blended ranking, true-negatives scored separately — explicitly flagged as placeholders.
- **Embedder question:** does the deterministic `HashingEmbedder` (feature-hashing, no model download) clear that bar, or is a real local embedding model needed behind the existing `Embedder` protocol? Trade-off is offline-simplicity vs. non-determinism-in-CI.
- **Weights:** `w_similarity=1.0, w_importance=0.35, w_recency=0.25`, 30-day recency half-life — explicitly untuned defaults, to be tuned only *after* the scenario set exists (not tuned-to-test).

Once the scoring bugs are fixed, this closes the "no live proof" gap the same way GSM8K/HumanEval already did for Phase 1. *Effort:* S (harness already supports it; run + read the output). *Kruz-gated:* No.
5. **Add Wilson/bootstrap confidence intervals to `metrics/core/aggregate.py`.** *What:* currently reports naked point estimates (e.g. "40%" on N=10, which is genuinely misleading at that sample size). *Why it matters:* This is explicitly named in Phase 3's own done-bar ("a comparison report with confidence intervals — not point estimates") — pulling it forward now means every benchmark run from this point on (including item #4's live BBH/IFEval runs) produces a trustworthy number immediately, rather than needing a re-run later once Phase 3 gets to it. *Effort:* M. *Kruz-gated:* No.
6. **Add an abstention/error bucket to aggregation.** *What:* `aggregate()` (`metrics/core/aggregate.py:37`) currently counts every non-correct result as wrong — a transient API error and a genuine wrong answer look identical in the report. There's also a dead `errored` variable already sitting unused at `make_grading_sheet.py:88`, suggesting this was anticipated but not finished. *Why it matters:* Understates capability on any run with API flakiness; directly relevant once this suite starts running unattended for the cross-cutting "which model should X use" use case, where a silent error-as-wrong-answer would misdirect a real model choice. *Effort:* S–M. *Kruz-gated:* No.
7. **Gate HumanEval's code execution behind an explicit flag + real sandboxing.** *What:* `benchmarks/standard/humaneval.py:93-103` runs model-generated code via bare `subprocess.run`, timeout-bounded but with no FS/network/syscall isolation — classic HumanEval RCE surface. Already honestly documented (docstring, README, STATUS) as a known-accepted risk for trusted models. Add `--allow-code-exec` as an explicit opt-in, and a container/firejail wrapper before ever pointing this at an untrusted or third-party model. *Why it matters:* Currently fine (only trusted models tested so far) but this is the biggest single exposure the suite carries if it's ever used to grade a model whose provenance isn't fully trusted — worth closing before Phase 3's "adversarial testing" phase makes that more likely. *Effort:* M (flag is S, real sandboxing is M-L depending on container availability). *Kruz-gated:* Soft — worth Kruz confirming the risk tolerance before this becomes load-bearing.
8. **Populate the ~24 empty `.gitkeep` scaffold directories per their mapped ROADMAP phase.** *What:* directory audit confirms these map cleanly to specific unbuilt work: `agents/{analyzers,benchmark_generators,meta_development,test_runners}` and `benchmarks/{agentic,custom}` + `metrics/{efficiency,reasoning}` = rest of Phase 2; `benchmarks/{robustness,safety}`, `metrics/{safety,plugins}`, `evaluation/adaptive`, `tools/{adversarial,synthetic_gen,visualization}`, `dashboards/` = Phase 3; `agents/meta_development` = Phase 4. One stray already-stale `.gitkeep` sits in `agents/judges/` despite that directory now having 5 real Phase 2 files — delete it. *Why it matters:* Not urgent on its own, but useful as a literal checklist for scoping Phase 2's remaining breadth (benchmark generators, agentic-category benchmarks, failure analyzers, efficiency profiling, basic safety/red-teaming — all explicitly listed in STATUS.md's "what's next" as unstarted). *Effort:* XL in aggregate (this is most of the remaining Phase 2+3 work), S for the immediate `.gitkeep` cleanup. *Kruz-gated:* No for cleanup; the breadth items are natural session-sized chunks, not individually gated.

## Cross-cutting: shared infra & dogfooding opportunities

These span two or more of the four projects and are generally higher-leverage per hour than any single project's Phase 3/4 work, because they make the *existing* Phase 1/2 output actually useful to something real — which is the explicit bar all four ROADMAPs share ("it must have answered a real question," "used on at least one real task," "made a real decision").

1. **Use llm-benchmark-suite to pick the model(s) the other 3 projects actually run.** All three of swe-agent-platform, research-agent-platform, and agent-os currently hardcode specific model IDs (`claude-opus-4-8` for swe-agent's live runs, `claude-sonnet-5` for research-agent's synthesis step, etc.) without any measured comparison. Once llm-benchmark-suite's calibration is trustworthy (item #1 above) and Phase 3 adds multi-model comparison, running a small task-relevant benchmark slice (e.g. code-repair tasks for swe-agent, long-context synthesis for research-agent) to justify or challenge those hardcoded choices is both a real-decision proof for llm-benchmark-suite's own Phase 4 bar *and* a legitimate model-selection upgrade for the other three. **Effort: M once llm-benchmark Phase 3 lands. Kruz-gated: which task slice counts as "representative" is a judgment call.**

2. **Point swe-agent-platform at real bugs already found in this portfolio, once its harder-task Phase 2 re-run (item #1 above) is designed.** The 2026-06-30 audit that grounds this whole report itself contains a ready-made task backlog of real, verified, file:line-cited bugs across `pc-bottleneck-analyzer`, `wishlist-tracker`, and elsewhere — e.g. wishlist-tracker's SSRF-in-price-fetcher or fail-open-auth findings are exactly the shape of well-scoped, verifiable (test-gated) real-world task swe-agent-platform's Phase 4 "used on at least one real task in your own portfolio" bar requires, and are meaningfully harder than the current 13-fixture set (real repo, real conventions, no seeded/synthetic bug). This can double as the harder-task-set decision in project 1's item #1 — instead of (or alongside) synthetic fixtures, feed it 2-3 of these real, already-triaged findings. **Effort: S to select tasks (they're already written up), M-L to actually run + verify. Kruz-gated: yes — approving swe-agent-platform to open a real PR against a real (non-fixture) portfolio repo is a trust decision, especially given the still-open finalize-safety-gap items in project 1.**

3. **A shared eval-harness pattern is emerging across three of the four projects independently — worth consolidating before it drifts.** swe-agent-platform's `harness.run_task` + `runner.compare` + `report.comparison_report` (materialize → run arm → score by real exit code → compare, deliberately not declaring a winner), llm-benchmark-suite's benchmark/adapter/judge pipeline, and agent-os's about-to-be-built recall-scenario harness (item #1 in project 3) are all solving the same shape of problem: run N scenarios through 1-2 arms, score deterministically, report without editorializing. None currently share code. Not urgent enough to block any current Kruz-gated decision, but worth a deliberate look once at least two of the three scenario-harness builds (swe-agent's is done, agent-os's is about to be built) exist side by side — likely candidate for a small shared `eval-harness-core` package or just a documented pattern, not a hard dependency. **Effort: M, purely opportunistic. Kruz-gated: no — but sequence after agent-os's harness exists so the abstraction isn't guessed from one example.**

4. **research-agent-platform's hybrid search (item #2, project 2) and llm-benchmark-suite's KB-adjacent needs both point at Atlas's schema.** research-agent-platform's KB was explicitly modeled on Atlas's SQLite+FTS5+local-embedding schema (confirmed in STATUS.md's "Overlap check" section) but doesn't share code with it. If llm-benchmark-suite's Phase 2 breadth items (analyzers, meta-development) end up needing similar local-recall infrastructure, there's a real chance of a third independent reimplementation of the same pattern. Worth a single line in whichever project builds it next: "check Atlas's actual module, not just its schema shape, before writing new code" — cheap insurance, no dedicated effort needed beyond that reminder. **Effort: negligible (a checklist item, not a build). Kruz-gated: no.**
